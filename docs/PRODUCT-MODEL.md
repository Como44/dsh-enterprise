# PRODUCT-MODEL —— DSH Enterprise（产品模型，人话版）

> 一句话定义：在 DSH 之上加一层「企业控制层」，把「我的 Agent 工具」变成「公司可以多人使用、共同沉淀 AI 能力、统一管理权限/资产/成本/外部账号的 AI 工作平台」。
> 参考样本不是答案：Accio Work Business（企业版）是当前最重要的对照样本，但每一项在这里都重新按 DSH 现实设计。

## 第一部分：对象模型（人话）

| 对象 | 人话解释 | 英文名 | 谁拥有 |
|---|---|---|---|
| 企业空间 | 公司的工作台，一切企业数据的根 | Organization | 公司（本机实现：一个企业空间可创建/切换） |
| 成员 | 使用企业工作台的人 | Member | 三个人类角色：老板(Owner)、管理员(Admin)、员工(Member) |
| 数字员工（Agent） | 由公司配置/员工创建的可复用角色，可开始对话 | Agent（对应 DSH AgentPreset） | 企业或创建者（见 ASSET-MODEL） |
| 方法（Skill） | 「怎么做某件事」的标准操作说明 | Skill | 企业共享为主 |
| 能力包（Plugin） | 一次交付的一组能力（含依赖） | Plugin | 企业 |
| 知识 | 公司事实/方法，Agent 引用时检索 | Knowledge | 企业（P1 最小版） |
| 外部账号 | 公司要连通的外部系统（店铺/GitHub/飞书…） | External Account | 企业；凭证在 DSH 凭据库 |
| 连接 | 一个外部账号的一条授权连接 | Connection | 成员发起、企业可见 |
| 资源范围 | 「这个连接能用哪些资源」的边界 | Resource Scope | 企业 |
| 工作区 | 项目文件与环境 | Workspace | 公司资源，分配给成员使用 |
| 会话 | 一次实际工作（与 DSH 一致） | Session | 按人归因，数据归企业（见下） |
| AI 资产 | 上面可复用能力（Agent/Skill/Plugin/Knowledge）的统一叫法 | Enterprise Asset | 按共享状态区分 个人/企业 |
| AI 使用额度 | 公司对 AI 花费的可见性与预算 | AI Compute Budget | 企业（成员额度 P1 只读） |
| 使用记录 | 谁、在哪个会话、用了什么模型、花了多少 | Usage Record | 企业（从 DSH 投影聚合，不重造） |
| 审计事件 | 谁做了什么管理动作 | Audit Event | 企业（P1） |

## 第二部分：回答那 14 个问题（系统答案）

1. **企业里"人"是什么对象？** → `Member`（角色三态）。人的痕迹＝成员标签绑在会话/资产/成本上；人离开企业，企业的数据不离开（见 6/7）。
2. **AI Agent 是员工、工具还是资产？** → 三重身份重叠，但按用途拆分：**对外是"数字员工"（可委派任务），对企业是"资产"（可拥有/共享/版本化），对系统是"角色"（DSH AgentPreset 的引用）**。管理上：资产优先；使用上：员工优先。
3. **Skill 是资产还是能力？** → 先资产后能力：在企业资产中心里它是"方法资产"（可共享/推荐/版本），被 Agent 引用后才是能力。
4. **Plugin 是工具还是资产包？** → 资产包（一组能力的交付单元）；企业层关注"企业允许哪些 Plugin 默认启用"（依赖治理 P2）。
5. **Knowledge 是谁拥有的？** → 企业的，不是个人的（公司事实标准统一）；个人草稿不进企业库。
6. **Workspace 是个人的还是公司的？** → 公司的（注册表由企业空间持有），但允许"个人工作区"存在；边界=分配关系。
7. **Session 离职以后属于谁？** → **数据属于企业**（会话日志在公司机器/路径上，归属于创建他的成员标签）；成员离职只影响"标签"与"私有资产"，不删除会话。
8. **AI 消耗是谁承担？** → 企业承担（额度从企业出），归因精确到 成员→会话→Agent→模型。
9. **一个企业如何控制 AI 成本？** → 三步：**看得见**（实时用量/成本面板）→ **设上限**（企业额度/预算规则，P1 预留，P2 强制执行）→ **告警**（P2）。
10. **管理员如何知道员工正在用 AI 做什么？** → 用量归因（谁/哪个 Agent/哪个模型/花多少）+ 会话可回溯（DSH 会话即审计底稿）。
11. **员工创造的 AI 方法如何沉淀成公司能力？** → 资产化四步：创建（个人私有，默认）→ 发布（转企业共享，可选管理员审核）→ 推荐/设为企业默认 → 使用与版本迭代。
12. **一个 Agent 如何安全访问企业不同账号？** → 三键绑定：Agent → Connection（凭证引用）→ Resource Scope（只给它需要的范围）；DSH 已有多凭证库与授权流。
13. **如何避免个人账号/企业账号/Agent 权限互相污染？** → 凭证只存 DSH 凭据库（引用不落盘）；每条连接有独立 Scope；Agent 只持有「绑定关系」而不是凭证；成员权限独立于连接授权（两道门）。
14. **企业如何形成越来越多、越来越好的 AI 资产？** → 生命周期闭环：创建→发布→推荐→使用→反馈迁移（更新 Skill/规则）→版本→归档；离职资产默认留企业（企业共享部分）。

## 第三部分：我们对 Accio 的批判（哪些不学）

| Accio 做法 | 我们的判断 |
|---|---|
| 积分=虚币，充值/套餐/平台 i豆两套货币 | **不学**：成本就用真实 API 价格 + 用量，透明可审计；额度是预算不是货币 |
| Agent Hub 市场 + 静默更新 | **不学**：企业内共享必须显式发布，禁止静默变更资产权限 |
| 供应链治理（签名/allowlist） | 学习方向（P2）：企业级 plugin 白名单 |
| 概念密度高（Agent/Skill/Plugin/MCP/Connector/Channel 边界难懂） | 学其教训：我们的 UI 用"资产中心"统一概念，能力状态卡（已安装→已绑定→已授权→可用）五道门可见 |
| 桌面端体验 | 不学：DSH 是 Web + LAN 网关，保持 Web-first |

## 第四部分：边界（本插件不做的事）

- 不做真实多人认证（DSH 本机单用户；多人身份 P2 接网关）；
- 不做充值/支付/账单（SaaS 商业模式不属于开源插件）；
- 不把知识库做成"检索系统"（P1 只做目录+索引声明，检索复用 DSH 会话搜索）；
- 不做业务垂直能力（国际站生意助手等属于它自己的 Connector 生态）。
